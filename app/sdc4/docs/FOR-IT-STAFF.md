# CordovaOS for the people who run it

A guide for engineers, data architects and platform staff evaluating what this
demonstration actually does, and what would change in your own estate.

CordovaOS is a fictional nation's government data platform: ten domain
applications, one reference model, one shared component library. It runs on your
machine with `make demo`. This document explains the parts that are easy to
miss, including several we got wrong ourselves and fixed in the open.

---

## 1. The applications are generated. The model is the source of truth.

All ten domains were generated by SDCStudio AppGen from SDC4-compliant data
models. Nobody wrote ten Django apps. That has a consequence worth stating
plainly: **when the model changes, the applications are regenerated, not
patched**. A change to a component is not a migration script and a sprint of
edits across ten codebases.

The practical test of this claim is in the repository: `app/sdc4/*/` are
generated, `app/sdc4/mediafiles/dmlib/` holds the published model per domain,
and every generated app reads its own schema from there.

## 2. One record, three projections, no ETL between them

Every instance is validated once and then written to PostgreSQL and to the
triple store from the same source. Open any record in the console at
`/console/` and switch between the tabs:

| Projection | Where it comes from | What it is |
|---|---|---|
| Document | `xml_content` | the authoritative artifact that was validated |
| Table | `json_instance` | a JSON projection generated from that XML |
| Graph | the named graph in GraphDB | RDF generated from the same XML |

There is no pipeline between them and no reconciliation step. The graph is not
a copy that drifts, it is a projection. This is the point that usually needs
seeing rather than explaining, which is why the console puts the three behind
one switch.

## 3. Absence is stated, never implied

This is the part most teams underestimate, and we got it wrong in this very
repository before we got it right.

The demonstration data originally wrote `"N/A"` into mandatory strings,
`1900-01-01` into mandatory dates, and `0.0` into a dosage field for patients on
no medication. Across ten domains that was 508 magic dates, 501 `"N/A"` strings
and zero Exceptional Values. Every one of those parses downstream as a real
value. A date of 1900 sorts, filters and charts. A zero dose averages.

There are two correct forms, and the difference matters:

- **Omission.** Most component references are `minOccurs="0"`. If a person has
  no vaccination, the record does not mention vaccination. This is valid and
  asserts nothing.
- **Exceptional Value.** When a value is *required* and missing, the record
  carries one of the sixteen ISO 21090 null flavors (`NI`, `NASK`, `ASKU`,
  `ASKR`, `NA` and the rest) naming the reason. **The instance is invalid, and
  that is correct.** An Exceptional Value explains a failure; it does not excuse
  one.

Seven records in this dataset are invalid on purpose to show that path. They
carry an `i-ev-` identifier prefix, so the fact survives outside the document,
and they are listed on the console's front page rather than hidden.

**What to check in your own data:** search for your sentinels. `9999-12-31`,
`-1`, `UNKNOWN`, `N/A`, `0` where zero is not a real quantity. Each one is a
question your schema cannot ask.

## 4. The join is the component, not a mapping table

Ten domains share a component library. Where two domains mean the same thing,
they restrict the *same published component*, not two local conventions that a
mapping table later reconciles.

Measured on this dataset:

| Component | Domains using it |
|---|---|
| Provenance set (`system_identifier`, `activity_*`, ...) | 10 |
| `City`, `Province` | 6 |
| `National ID (CID)` | 4 |
| `organization_identifier` | 3 |

The console's cross-domain question at `/console/question/` joins 250 people
across 883 records in about a seventh of a second, with no mapping table,
because the identifier *is* the join. 75 of those people appear in four
separately built systems.

## 5. Governance is read from the published schema

Select any field in the table projection and the console reports what the model
permitted it to hold: the reference model type it restricts, the facets on its
value, whether the value is required, its units, whether an absence may be
stated, the definition, and the external binding.

For Body Temperature in the healthcare model that is `XdQuantityType`,
`minInclusive 30.00000`, `maxInclusive 45.00000`, units `Temperature (SI -
Metric)`, value required, Exceptional Value permitted, bound to an NCBI
reference.

None of that is a description someone maintained separately. It is parsed from
`dm-{ct_id}.xsd`, the same file a counterparty validates against. **A resource
view in a triple store shows what a node asserts. This shows what the schema
permitted it to assert**, which is the question an auditor is actually asking.

## 6. Operational notes, learned the hard way

Things that will bite you, all of which bit us:

- **An invalid instance is not projected to the triple store.** Correct
  behaviour, and it means those records exist in PostgreSQL only. Do not build a
  SPARQL query on stage expecting to reach one.
- **This stack runs with no outbound network.** The validator falls back to the
  local schema when it cannot resolve `semanticdatacharter.com`, and all CSS and
  JS are vendored under `static/vendor/` rather than pulled from a CDN. If you
  are evaluating for an air-gapped deployment, unplug the network and reload.
- **`settings._discover_local_apps()` scans every directory with an `apps.py`.**
  A hand-registered app must also be added to that function's skip set, or
  Django refuses to start with "Application labels aren't unique", which kills
  the container and takes the autoreloader with it.
- **Parties are not components.** `subject` and `provider` are native reference
  model types, so anything they carry, including a `party-ref`, needs explicit
  handling in the RDF extractor. A reference that exists in the XML and not in
  the graph is invisible to exactly the queries you built the graph for.
- **★ Keep schema resolution local, or validation stops being deterministic.**
  Every generated data-model schema carries
  `<xsd:include schemaLocation="https://semanticdatacharter.com/ns/sdc4/sdc4.xsd"/>`.
  If that include is fetched over the network and the fetch fails, the reference
  model's substitution groups are unknown, and instances that are perfectly
  valid are reported invalid. We hit this here: five records across four domains
  were stored as invalid and re-validated clean afterwards, because whether a
  DNS lookup succeeded decided the verdict. That is the failure this project
  argues against, in its own loader.
  **`mediafiles/dmlib/catalog.xml` fixes it**: one OASIS catalog with relative
  entries, mapping the reference model and the data-model library, so the
  mapping travels with the library and works on an air-gapped host. The
  validator reads it and warns if it ever falls through to the network.
- **Clearing loaded data means clearing the triple store too.** `load_all_data
  --clear` deletes rows; named graphs are separate. Each load mints new instance
  identifiers, so without explicit clean-up every reload abandons a full
  generation of graphs that PostgreSQL cannot see and SPARQL can. Six loads here
  left 7,272 orphaned graphs against 1,446 live instances, and every
  cross-domain count taken off the graph was inflated roughly six-fold until it
  was found.

## 7. What this demonstration does not show

- The dataset is synthetic. Cordova is a fictional country.
- The exposure narrative reaches Healthcare, Maritime, Civil Registry and
  Education. It does not reach Tax, so the "trade at risk" style question is not
  answerable here and the console says so on the page rather than staging it.
- Load times are dominated by validation and dual-writing, not by generation.
  The small dataset takes a few minutes; the 25,000-resident set takes hours.

## Running it

```bash
git clone https://github.com/Axius-SDC/CordovaOS.git
cd CordovaOS
make demo          # Docker, ~6GB RAM, a few minutes
```

Then open `http://localhost:18000/demo/` for the domain dashboard and
`http://localhost:18000/console/` for the record explorer.
