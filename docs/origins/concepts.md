# SDC Cross-Domain Interoperability Demo — "Cordova OS"

In late 2025, the Republic of Cordova re-chartered its ten government information systems under the Semantic Data Charter (SDC4). Each domain — from Civil Registry to Maritime Port Authority — was modeled in SDCStudio and compiled into a unified Django project: **Cordova OS**. The old systems were siloed, incompatible, and query-blind across domains. The new architecture shares a single Reference Model, a single graph database, and a single set of ontologies — with zero integration code between domains.

Two months later, in January 2026, a sick crew member arrived at Porto Sereno aboard a cargo vessel. The cross-domain infrastructure Cordova had just built was tested under real pressure for the first time.

**The goal of this demo:** Showcase cross-domain interoperability of SDC — proving that a single Reference Model can power 10 completely different domain applications, and that a graph database can answer questions that span all of them in a single query.

> **About this repo:** This repository contains the design documents, SDCStudio import templates, and (eventually) the generated Cordova OS Django project. It will be deployed as a full demo on GCP with GraphDB and Graphwise dashboards.

## Architecture: One Django Project, Ten Generated Apps

This demo is **not** ten separate applications stitched together with glue code. It is one Django **project** — "Cordova OS" — containing ten Django **apps**, each generated by SDCStudio from its own data model.

### How It Works

1. **SDCStudio** is used to design each domain's data model (Civil Registry, Healthcare, Maritime, etc.)
2. SDCStudio's **App Generator** produces a Django app for each model — forms, validation, RDF triple emission, and all
3. All ten generated apps are installed into a single Django project: `cordova/`
4. The project provides the shared shell: authentication, DPV role selection, navigation, and the connection to the shared GraphDB triple store
5. Each app writes RDF triples to the **same** GraphDB instance using predicates and types from the **same** SDC4 Reference Model and ontologies

### Why This Matters

**There is no glue code.** No middleware. No API adapters. No message buses. No ETL pipelines. No data mapping layer.

The ten apps interoperate because they were all compiled from the same Reference Model (SDCRM). The Person cell in Civil Registry is structurally identical to the Person cell in Healthcare, Employment, Law Enforcement, and Maritime. They share the same RDF predicates, the same XSD types, the same `act` elements. A SPARQL query that traverses from a Maritime crew list to a Civil Registry identity to a Healthcare record works **because the schema compiler guarantees structural compatibility** — not because someone wrote integration code.

This is the core proof point of the demo: **the interoperability is in the compiler output, not in custom integration work.**

### What the Investor Sees

If we built one monolithic app with ten tabs, investors would think: "They wrote a big app." If we built ten separate apps with REST APIs between them, investors would think: "They wrote a lot of integration code."

Instead, they see ten independently generated apps — each with its own models, forms, and validation — that query across each other's data in a single SPARQL traversal. The natural question is: "How?" The answer is: "The Reference Model is the integration layer. SDCStudio compiled it in."

## Demo Narrative: "The Contagion"

Static records are boring. The demo needs a **trigger event** that forces the domains to interact, making interoperability visceral rather than theoretical.

### The Scenario

1. **Port Authority:** A cargo vessel, *MV Estrella del Sur*, arrives at Porto Sereno. A crew member — Carlos Mendoza — reports sick during customs inspection.
2. **Healthcare:** Carlos is admitted to Porto Sereno General Hospital. His medical cell carries `Restricted:PatientCare` policy.
3. **Civil Registry:** Carlos has family in Novaciudad. His sister, Elena Mendoza, is a teacher at Universidad Nacional de Cordova in Campoluz.
4. **Law Enforcement:** Provincial health authority establishes a quarantine monitoring zone around the port district.
5. **The Crisis:** The Governor (playing the **Auditor** role) needs to identify all contacts — but the medical diagnosis is redacted per the `act` rules.

### The "Ah-Ha" Moment

The Auditor runs a single SPARQL query that traverses Maritime (crew manifest) → Civil Registry (family relationships) → Employment (Elena's workplace) → Education (university campus contacts). The query returns:

> "Carlos Mendoza arrived on MV Estrella del Sur on January 15. He has one family contact in Novaciudad: Elena Mendoza, employed at Universidad Nacional de Cordova, Campoluz. **Medical diagnosis: REDACTED — Purpose Mismatch.**"

The Auditor can see *where* patient zero went and *who* he contacted — but **not** his diagnosis. The DPV role-based access is doing exactly what it should: enabling public safety response while protecting medical privacy.

To see the diagnosis, the Auditor would need to invoke a **Governed Override**, which creates an `Exception:Override` Cell — itself a governed, auditable object in the graph.

### The Refusal Moment

The demo must also show **what SDC won't do.**

1. Switch to the **Healthcare Provider** role.
2. Attempt to compose Carlos's HIV test result (a `Restricted:PatientCare` cell) into a public health marketing report.
3. The system **rejects the composition at the schema level** — not with a UI error message ("Permission Denied"), but with a **Schema Validation Failure**.
4. Show the raw validation output: the data *itself* carried the `Restricted:PatientCare` policy and refused to bind with the Public Marketing context.
5. The failure creates an ExceptionalValue object — structured, governed, auditable. Not an error log. A first-class Cell.

**This is Data Physics.** The data doesn't just sit there waiting for application code to protect it. The data *enforces its own constraints*.

### DPV Redaction Tooltips

When any role views a record containing cells they don't have clearance for, the redacted cells show a tooltip on hover:

```
Access Denied
  User Role: dpv:HealthcareOrganisation
  Data Purpose: dpv:EnforceLaw
  Reason: Purpose Mismatch (dpv:ProvideHealthcare ≠ dpv:EnforceLaw)
```

This makes the invisible governance layer tangible. The user sees *why* the data is hidden, using standardized W3C vocabulary — not a cryptic permission code.

## Domain Applications (10 Domains)

Each domain gets its own SDCStudio-generated Django app with its own data models. All share the same SDCRM foundation. All emit RDF triples to the shared GraphDB instance.

### 1. Civil Registry

**Purpose:** The authoritative source of identity for every person in Cordova.

**Records:**
- Full name (first, middle, last)
- National ID (CID)
- Date of birth, place of birth
- Gender
- Current address (city, province)
- Phone number(s), email address(es)
- Familial relationships (parent-child, spouse, sibling)
- Marital status and history

**SDC Showcase:** The Person cell appears across every other domain. This is the anchor node in the graph — proving that a single identity model can be referenced by healthcare, law enforcement, tax, property, and every other system without duplication or reconciliation.

---

### 2. Vital Statistics

**Purpose:** Government registry of life events as formal attested records.

**Records:**
- Birth certificates (linked to parents, attending physician, location)
- Death certificates (cause of death, certifying physician, date/location)
- Marriage certificates (both parties, officiant, witnesses, date/location)
- Divorce decrees (both parties, decree date, court)

**SDC Showcase:** Temporal events with full Attestation and Participation. Each vital record has a formal chain of who created it, who attested to it, and when. Demonstrates the Audit and Attestation components of SDCRM — these aren't just data rows, they're governed legal events.

---

### 3. Healthcare

**Purpose:** Basic medical records for every person.

**Records:**
- Primary care provider assignment
- Allergies and chronic conditions
- Medication list (current)
- Vaccination history
- Visit records (date, provider, facility, reason, diagnosis, outcome)
- Basic lab results (blood type, common panels)
- Height, weight, vital signs history

**SDC Showcase:** Demonstrates ExceptionalValue handling — lab results with out-of-range values get quarantined and tagged, not discarded. Also showcases privacy constraints: medical cells carry `Restricted:PatientCare` policy that prevents unauthorized composition with public data.

---

### 4. Education

**Purpose:** School enrollment, certifications, and academic records.

**Records:**
- Primary/secondary school enrollment (school, years attended, graduation)
- University enrollment (institution, program, years, degree awarded)
- Professional certifications (type, issuing body, date, expiration)
- Continuing education / training records

**SDC Showcase:** Links people to institutions and creates a credentials-to-skills pipeline that connects to employment records. A graph query can trace: Person -> Degree -> Skills -> Employment -> Business — across four domain apps in one traversal.

---

### 5. Employment

**Purpose:** Work history and skills registry for working-age adults.

**Records:**
- Employer (linked to Business Registry)
- Job title, department
- Start date, end date (null if current)
- Skills inventory (standardized skill codes)
- Salary band (not exact salary — range codes)
- Employment status (full-time, part-time, contract, self-employed)

**Coverage:** ~70% of adults (18+) have at least one employment record. Some have multiple (job history). Unemployment rate ~8%.

**SDC Showcase:** Cross-references Business Registry (employer), Education (qualifications), and Tax/Revenue (income reporting). Demonstrates how the same Person cell participates in completely different domain schemas.

---

### 6. Business Registry

**Purpose:** Company incorporation and governance records.

**Records:**
- Business name, registry number (BIZ-NNNNNN)
- Date of incorporation
- Business type (sole proprietor, partnership, corporation, cooperative)
- Registered address (city, province)
- Officers and directors (linked to Civil Registry)
- Industry classification code
- Active/dissolved status

**Coverage:** ~1,500 businesses across all nine cities. Porto Sereno and Novaciudad have the highest concentrations.

**SDC Showcase:** Officers/directors are Person cells from Civil Registry. Demonstrates that the same identity model works for both personal and corporate governance contexts without modification.

---

### 7. Property Registry

**Purpose:** Land and property ownership, transfers, and liens.

**Records:**
- Property identifier (parcel number)
- Property type (residential, commercial, agricultural, government)
- Location (address, city, province)
- Current owner(s) (linked to Civil Registry or Business Registry)
- Transfer history (buyer, seller, date, price, notary attestation)
- Liens and encumbrances
- Assessed value (for tax purposes)

**Coverage:** ~8,000 properties across all cities. Most adults own or co-own at least one property.

**SDC Showcase:** Ownership can be a Person or a Business — both are valid owner types because they share the same Reference Model. Transfer records demonstrate full provenance chains with Attestation (notary).

---

### 8. Tax & Revenue

**Purpose:** Tax filings linked to employment, property, and business ownership.

**Records:**
- Annual tax filing (person, tax year, filing status)
- Employment income (linked to Employment records)
- Property tax assessments (linked to Property Registry)
- Business tax filings (linked to Business Registry)
- Tax payment history (amount, date, method)
- Outstanding balances / payment plans

**SDC Showcase:** The killer cross-domain query: "Show me all revenue-generating relationships for Person X" — pulls from employment income, property assessments, and business dividends in a single SPARQL traversal. This is impossible in siloed systems.

---

### 9. Law Enforcement

**Purpose:** Misdemeanor arrest and citation records.

**Records:**
- Incident report (date, time, location, reporting officer)
- Arrested person (linked to Civil Registry)
- Charge(s) — misdemeanors only (petty theft, public intoxication, trespassing, disorderly conduct, traffic violations, minor vandalism)
- Disposition (fine, community service, case dismissed, pending)
- Fine payment status

**Coverage:** ~5-8% of adults have at least one record. No felonies in Cordova. Repeat offenders are rare but present.

**SDC Showcase:** Demonstrates constrained composition — a law enforcement cell with `Restricted:LawEnforcement` policy cannot be composed into a public-facing report without the parent schema catching the policy collision. The "Conflict of Laws" pattern in action.

---

### 10. Maritime / Port Authority

**Purpose:** Ship traffic at Porto Sereno, the national port.

**Records:**
- Vessel registry (name, flag state, IMO number, type, tonnage)
- Port calls (vessel, arrival date/time, departure date/time, berth assignment)
- Cargo manifests (vessel, cargo type, quantity, origin, destination)
- Crew lists (linked to persons — some Cordovan nationals, some foreign)
- Port fees and payments (linked to shipping companies in Business Registry)
- Customs declarations

**Coverage:** ~200 vessels making ~2,000 port calls per year. Mix of cargo, fishing, and passenger vessels.

**SDC Showcase:** Connects maritime operations to the business graph (shipping companies), person graph (crew), and tax graph (port fees). A supply chain provenance query: "Trace cargo from vessel arrival through customs declaration to business receipt to tax filing."

## GraphDB & Graphwise Integration

### Architecture

```
SDCStudio (Data Model Design)
         |
         | App Generator
         v
Cordova OS (1 Django project, 10 generated apps + shell)
         |
         | RDF Triples (per record, same SDCRM predicates)
         v
    GraphDB (shared triple store)
         |
         | SPARQL Endpoint (role-filtered via act/DPV)
         v
    Graphwise Dashboards
```

**Why cross-domain queries work:** Every generated app uses the same SDC4 ontology URIs. A `Person` in `civil_registry` and a `Person` in `healthcare` share the same RDF type and predicates because they were compiled from the same Reference Model. GraphDB doesn't need a mapping layer — the triples are structurally compatible by construction.

### Pre-Built Cross-Domain Queries

These are the demo's headline features — queries that are impossible in siloed systems but trivial in the graph:

**1. "Complete Government Profile"**
Show all government touchpoints for Person X — medical records, tax filings, property ownership, vehicle records, education history, employment, vital events, and any law enforcement records. One query, ten domains.

**2. "Economic Network Analysis"**
Trace the economic network around Business Y — employees, tax filings, port shipments received, properties owned, officers and their other business affiliations. Renders as a force-directed graph in Graphwise.

**3. "Social Services Identification"**
Find all people in City Z with medical records indicating chronic conditions AND no current employment record AND no property ownership. Cross-domain pattern matching for social services outreach.

**4. "Supply Chain Provenance"**
Track a ship's cargo manifest through port entry -> customs declaration -> business receipt -> tax filing. End-to-end provenance across four domain apps.

**5. "Family Economic Unit"**
Given a person, find their entire family unit (Civil Registry relationships), aggregate all employment income, property ownership, tax filings, and education levels. A complete household economic picture from six domain apps.

**6. "Institutional Impact"**
For Universidad Nacional de Cordova: find all graduates, their current employers, their employers' tax contributions, and any businesses they've founded. Measures the economic impact of an institution through the graph.

## Role-Based Access Control via DPV

Users must select a **role** when accessing the demo. The role determines which data cells are visible, which are redacted, and which are completely hidden. This is enforced through the `act` (access control tag) elements on each Cell, using vocabulary from the [W3C Data Privacy Vocabulary (DPV) 2.2](https://w3c.github.io/dpv/2.2/dpv/).

### How It Works

Each SDC Cell carries `act` metadata that declares:
- **Purpose** — why this data exists (from `dpv:Purpose` taxonomy)
- **Legal Basis** — the lawful justification for processing (from `dpv:LegalBasis`)
- **Allowed Roles** — which entity roles may access this cell (from `dpv:Entity` taxonomy)

When a user selects a role, the system evaluates every Cell's `act` against that role. Cells where the role is not in the allowed set are either hidden entirely or redacted to show only that a record exists without revealing content.

This is not application-level filtering. The access constraints are **part of the data itself** — they travel with the Cell across systems, into the graph, and through any composition.

### Demo Roles

The demo offers 8 roles. Each maps to DPV entity types and sees a different slice of the same 10-domain dataset.

| # | Role Name | DPV Entity Type | Description |
|---|-----------|----------------|-------------|
| 1 | **Citizen** | `dpv:DataSubject`, `dpv:Citizen` | A resident viewing their own records. Sees their own data across all domains but cannot see other people's records. The "my data" view. |
| 2 | **Healthcare Provider** | `dpv:DataController`, `dpv:HealthcareOrganisation` | A physician or clinic staff member. Sees patient medical records, vital statistics (birth/death certificates), and limited civil registry data (name, DOB, allergies). Cannot see tax, employment, law enforcement, or property records. |
| 3 | **Law Enforcement Officer** | `dpv:DataController`, `dpv:LawEnforcementOrganisation` | A police officer or investigator. Sees law enforcement records, civil registry (identity verification), and maritime crew lists. Cannot see medical records, tax filings, or education details. |
| 4 | **Tax Authority** | `dpv:DataController`, `dpv:GovernmentalOrganisation` | A revenue service official. Sees tax filings, employment income, property assessments, business registry, and port fees. Cannot see medical records or law enforcement records. |
| 5 | **Port Authority** | `dpv:DataController`, `dpv:GovernmentalOrganisation` | A customs/port official. Sees vessel registry, port calls, cargo manifests, customs declarations, crew lists, and linked business records (shipping companies). Limited civil registry access for crew identity verification. |
| 6 | **Civil Registrar** | `dpv:DataController`, `dpv:GovernmentalOrganisation` | A government records administrator. Full access to civil registry and vital statistics. Read-only summary access to other domains (can see that records exist but not their content). |
| 7 | **Employer / HR** | `dpv:DataController`, `dpv:ForProfitOrganisation` | A business HR department. Sees employment records for their own company's employees, education/certification verification, and business registry data. Cannot see medical, tax, law enforcement, or property records. |
| 8 | **Auditor** | `dpv:DataController`, `dpv:Authority` | A cross-domain oversight role. Can see all records across all domains but only the **metadata and provenance** — Audit trails, Attestation chains, and Participation records. Cannot see the actual data content. Proves that governance is observable without exposing private information. |

| Civil Registry | Full | Limited | Identity | Identity | Crew ID | Full | Verify | Provenance |
| Vital Statistics | Full | Full | -- | -- | -- | Full | -- | Provenance |

| Education | Full | -- | -- | -- | -- | -- | Verify | Provenance |
| Employment | Full | -- | -- | Income | -- | -- | Own staff | Provenance |
| Business Registry | Full | -- | -- | Full | Shipping co. | -- | Own co. | Provenance |
| Property Registry | Full | -- | -- | Full | -- | -- | -- | Provenance |

**Key:**
- **Full** — complete read access to all fields
- **Limited** — select fields only (e.g., name, DOB, allergies for healthcare)
- **Identity** — name and national ID only, for verification
- **Verify** — can confirm a record exists, see credential type and status, but not full content
- **Income** — employment income figures only, not job details
- **Own staff / Own co.** — scoped to records related to their own organization
- **Crew ID** — identity verification for vessel crew members
- **Shipping co.** — business records for shipping/logistics companies only
- **Port fees** — financial records related to port operations only
- **Provenance** — Audit, Attestation, and Participation metadata only; no data content
- **--** — no access; cell is completely hidden

### Governed Override (ExceptionalValue in Action)

When a role attempts to access a Cell they don't have clearance for, the system does not silently fail. Instead:

1. The Cell is hidden per the `act` rules
2. If the user invokes an **override** (e.g., a physician needs law enforcement context for a patient safety situation), the system creates an `Exception:Override` Cell containing:
   - The requesting user's identity and role (`dpv:DataController`)
   - The target Cell reference (what they want to see)
   - The justification (`dpv:Purpose` for the override)
   - The legal basis claimed (`dpv:LegitimateInterest` or `dpv:VitalInterest`)
   - Timestamp and `dpv:ConsentRecord` if applicable
3. The override itself becomes a governed, auditable object in the graph
4. The **Auditor** role can see all override events across the system

This demonstrates that even access control exceptions are first-class citizens in SDC — they don't escape the physics.

## SDC Interoperability Proof Points

The demo should make these points undeniable:

1. **Same Person, Ten Systems** — One Person cell (same SDCRM type) works identically across healthcare, tax, law enforcement, maritime, and every other domain. No mapping. No reconciliation. No ETL.

4. **Graph-Native Queries** — Questions that require joining 4-6 relational databases become single SPARQL queries because every Cell shares the same Reference Model.

6. **Zero Integration Code** — No middleware, no API adapters, no message buses between domains. The interoperability is structural, not plumbing. Ten Django apps in one project with **no glue code** — the SDC4 Reference Model and ontologies are the integration layer. The compiler guarantees structural compatibility at generation time.

7. **Role-Based Visibility from the Data, Not the App** — Access control is declared in the Cell's `act` elements using W3C DPV vocabulary. The same graph, the same queries, the same dashboards — but eight different views depending on who is looking. The access rules travel with the data, not with the application. Redacted cells show DPV-vocabulary tooltips explaining *why* access was denied.
